FASE 5 - HDFS, KAFKA Y MONGODB
==============================

ESTADO HDFS
-----------
Se comprobó en WebHDFS que /user/iabd-user11/reto1 contiene la carpeta
originales con seis directorios: emal, etxebide, eustat, fotocasa,
otras_fuentes y pisos. La carga anterior del notebook informó 269 archivos
y 136.091.377 bytes. No se repitió la carga, a petición del usuario.

El archivo de entrada Pisos.com existe en HDFS:
/user/iabd-user11/reto1/originales/pisos/pisos_euskadi.csv
Su tamaño remoto y local es 195.471 bytes; se leyó desde HDFS y se validaron
sus 1.041 filas y cabeceras.

El estado remoto consultado solo muestra originales; no se creó ni subió otra
carpeta HDFS. El manifiesto local del cargador se ajustó para excluir
subcarpetas Fotocasa/pruebas y HTML notFound en futuras cargas. En HDFS ya
había cinco HTML de pruebas, que no se borraron ni modificaron.

FLUJO EJECUTADO
---------------
HDFS (CSV original Pisos.com)
    -> productor Python
    -> tópico Kafka
    -> consumidor Python
    -> MongoDB

El CSV original contiene 1.041 filas y 1.041 URL únicas: 822 anuncios de
venta y 219 de alquiler. El productor los publica como JSON y usa SHA-256 de
la URL como event_id determinista. Se etiqueta el evento como
reproduccion_historica: son anuncios reales reproducidos desde el snapshot,
no anuncios nuevos inventados.

El CSV no incluye codigo_municipio. El flujo no infiere ni inventa códigos;
conserva localidad_zona como texto y deja ausente municipio_codigo.
Los campos numéricos interpretables se convierten a número y los valores
vacíos se mantienen como nulos.

Kafka:
- Tópico: reto1_anuncios_iabd-user11
- Particiones: 1
- Replicación configurada: 1
- Mensajes de anuncios confirmados por el productor: 1.041
- El consumidor se inicia antes que el productor y confirma el lote completo.

MongoDB:
- Base: reto_vivienda_fase3
- Colección nueva: anuncios_stream_fase5
- Resultado: 1.041 recibidos, 1.041 insertados y 0 existentes en la primera
  ejecución; 1.041 event_id distintos.
- La colección canónica anuncios_pisoscom permanece en 1.041 documentos.
- La clave _id determinista y $setOnInsert hacen idempotente la ingesta.

DEPENDENCIAS Y EJECUCION EN WINDOWS
-----------------------------------
Desde la raíz Reto1, instalar:

    .\.conda\python.exe -m pip install -r .\requirements-fase5.txt

Crear o verificar el tópico:

    .\.conda\python.exe -B .\src\fase5_streaming.py crear-topic

Abrir dos terminales desde la raíz. En la primera:

    .\.conda\python.exe -u -B .\src\fase5_streaming.py consumidor

Cuando indique que está listo, ejecutar en la segunda:

    .\.conda\python.exe -u -B .\src\fase5_streaming.py productor

El usuario HDFS, los endpoints, el tópico, MONGO_URI y otros valores admiten
configuración mediante variables de entorno. Los valores por defecto del
proyecto apuntan a la infraestructura previamente utilizada.

DECISION TECNICA
----------------
La instalación de confluent-kafka falló en el Python 3.15 del proyecto porque
su extensión nativa requiere Microsoft Visual C++ 14. Se utilizó
kafka-python (cliente Python puro), compatible con el entorno disponible.
El cargador histórico de archivos ya se había ejecutado y verificado, por lo
que no se volvió a ejecutar ni se borró contenido HDFS.

VALIDACION
----------
- Diez pruebas unittest pasan.
- Se ejecutó el flujo real HDFS -> Kafka -> MongoDB.
- 1.041 mensajes fueron recibidos y correspondieron a 1.041 documentos con
  identificadores únicos.
- 69 precios, 8 habitaciones, 12 baños, 35 superficies y 104 precios por m2
  permanecieron nulos cuando faltaban en el CSV.
- No se añadió codigo_municipio a ningún documento del flujo.

Limitación: como el archivo original no contiene códigos municipales, esta
colección de streaming no sirve por sí sola para análisis municipal. Para esos
análisis se mantiene la colección geolocalizada canónica de la Fase 3.
